# 领域文档流程

仅在发现领域文档，或用户要求记录领域决策时加载。本流程用于校准设计语言与已有约束；是否写文件由当前任务授权决定。

## 找到相关上下文

- 根目录存在 `CONTEXT-MAP.md` 时，先读取映射，沿链接找到当前功能所属上下文及直接交互方。
- 只有根目录 `CONTEXT.md` 时先按单上下文处理；发现模块自己的领域文档时尊重其边界。
- 阅读相关上下文及系统级 `docs/adr/` 中影响当前问题的决策，注意替代、废弃或提案状态。
- 用户要求落盘且没有现有文档时，只在形成有用内容后创建必要文件，不预建整套目录。

## 用文档检验设计

1. 核对概念是否同义、重名或跨上下文异义。例如“账户”可能指登录身份，也可能指结算账户。
2. 对照业务关系检查所有权、基数、生命周期与不变量；用具体场景检验部分完成、重复事件或跨边界失败。
3. 对照代码与测试确认当前行为。发生冲突时并列呈现依据，明确哪部分是事实、期望或尚未确认的假设。
4. 碰到既有 ADR 的限制时解释原取舍与新方案的差异；不能仅凭新方案方便就默认推翻已接受决策。
5. 需要用户选择时回到入口的逐项追问流程，每次一个问题并提供推荐答案。

## 获准后记录术语与关系

优先遵循已有文档结构，不强制将项目现有 `CONTEXT.md` 改成某种模板。
新增领域词汇表时，记录上下文的用途、核心术语的简洁定义、容易混淆的别名，以及业务关系和必要基数。
用少量具体业务例子澄清边界；通用编程术语、实现细节与临时讨论记录不放入领域词汇表。
多上下文场景允许同一词有不同定义，应注明语境；不要为追求统一名称抹去真实业务差异。
只有上下文边界或交互关系确实变化时才同步 `CONTEXT-MAP.md`。

## 获准后记录架构决策

优先记录难以逆转、未来读者容易误解且经过真实取舍的决定；项目已有 ADR 规范时以其为准。
普通命名或显而易见的实现选择无需单建 ADR。

最小内容是背景、决定、选择原因与重要后果；只有拒绝理由值得保存时才展开备选方案。
延续已有命名及编号规则，创建前检查编号是否已被占用。
改变历史决策时新建替代记录并标明关系，保留旧记录的历史含义，不静默覆写。
未确认的选项标记为提案或待定，不能写成已接受决定。
