# 设计评审

把方案中的关键假设变成有依据的决策，形成可继续设计或实施的共识。
沿用用户给出的范围、限制和已经确认的答案，不重新开展需求访谈。

## 确定评审依据

1. 从对话与方案中提取目标、成功标准、约束、已确认决策和未决问题。
2. 有仓库时先看任务相关代码、测试与项目说明；代码能回答的问题先查代码。
3. 检查仓库根及相关模块的 `CONTEXT.md`、`CONTEXT-MAP.md`、`docs/adr/`。
4. 发现上述文档，或用户要求记录领域决策时，读取 [领域文档流程](references/domain-docs.md)。
5. 没有领域文档时直接评审；不初始化文档目录或工单配置。

只读取当前设计涉及的上下文与决策，不为评审遍历所有领域文档。
区分代码当前行为、文档规定、用户期望和自己的推断，避免把实现现状当成需求。

## 逐项解决决策

- 按依赖关系先处理会改变后续选择的决策，例如所有权、状态边界与外部契约。
- 每次只提出一个实质问题；给出推荐答案、理由和最重要的代价，等待回答再进入依赖问题。
- 使用具体输入、事件顺序、失败恢复或反例检验方案；优先检查影响正确性与实现范围的情况。
- 发现矛盾时引用代码或文档证据，说明会导致什么不同结果，再请用户决定需求含义。
- 仅实现细节且已有明确约定的事项自行判断；不要把普通工程选择逐项变成确认请求。
- 对已经回答的问题只在新证据改变结论时重开，并说明新证据。

维护简短的“已确认／待确认”记录，避免重复追问；复杂方案按分支推进。
不使用固定问题数量，也不为了“全面”穷举与当前目标无关的情况。
用户只要求评审报告时直接交付发现和建议，将无法判断的关键问题列为未决项。

## 文档与授权

纯评审、讨论或请求建议只在对话中交付，不自动修改 `CONTEXT.md`、ADR 或代码。
用户要求更新文档、落实已确认决策时，按现有格式持久化相关内容。
已有授权无需再次确认；新术语或方案仍有歧义时，先解决含义再写成已接受决策。
不因为代码与文档冲突就改文档迁就实现，也不把讨论中的选项记作正式决定。

## 完成条件与交付

关键目标、边界、主要取舍和验收方式已明确后结束，不要求额外口令或形式审批。
仍需外部事实或用户选择时，说明具体缺口及其影响，继续完成不依赖它的评审部分。

交付与任务规模相称的结论：

- 已确认的设计与推荐取舍，以及支撑结论的代码或文档位置。
- 有实际影响的问题、未决项和下一步；没有问题时不凑条目。
- 获准修改文档时列出实际变更；未完成决定明确保留为待确认。
