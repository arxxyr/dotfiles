# 版本、打包与发布

完成用户请求范围内的版本与产物工作；准备产物不自动授权推送标签、发布或部署。
已有明确授权持续有效；新项目使用以下默认约定，既有项目保持其发布协议。

## 版本决策

- 先定位唯一权威版本来源和消费方，读取当前版本；共享版本的应用不新增第二份定义。
- 用户指定目标版本优先，执行前简短说明“当前版本 → 目标版本”。
- “小版本”、`bump patch`、补丁号加一都是 PATCH + 1，包括 `0.x`。
- `bump minor` / 次版本号加一递增 MINOR 并清零 PATCH。
- `bump major` / 主版本号加一递增 MAJOR 并清零 MINOR/PATCH。
- 未指定级别且仅兼容修复、解析修复或 CI/构建修正时默认 PATCH。
- 新功能和不兼容变化按实际发布范围判断，不从单独一个“bump”推断 MINOR 或 MAJOR。
- 新建多模块应用默认统一版本；不要迁移已有独立发布包的版本策略。

## 同步范围

- 修改权威来源，同步应用锁文件中的本项目版本及当前发布示例。
- 使用项目工具更新锁文件，不手改 `uv.lock`，不顺带升级第三方依赖。
- 保留历史记录和固定测试样例中的版本；处理动态生成文件时修改其生成源。
- 检查 CI、安装脚本和应用内版本展示是否仍消费同一权威值。

## 按需参考

- 调整产物命名、包内容、压缩或本地部署：读取 [产物与部署](references/packaging.md)。
- 创建或修改流水线、上传产物或创建 Release：读取 [发布流水线](references/ci.md)。
- Rust 的 lint、缓存、timings 与工具链能力可用 `rust-engineering`。
- CMake 预设、LTO 和平台构建可用 `cpp-engineering`。
- 不因为修改版本号就初始化工单系统或启动完整团队流程。

## 执行边界

- 用户已要求发布、推送或部署时完成授权范围，不重复询问已有授权。
- 未授权外部写入时，先完成可审查的本地产物和变更；只有确需新的授权才询问。
- 不覆盖已发布的标签或产物来修补错误；先确认确切目标和恢复方式。
- 外部操作结果不确定时先查询状态，避免重复创建 Release 或重复部署。

## 验证与交付

- 确认版本来源、产物文件名、包内 VERSION 和运行时显示一致。
- 验证包内仅含交付所需内容，并在实际可用平台执行基本启动检查。
- 报告版本变化、检查结果、产物位置和已执行的外部动作；未发布明确说明。
