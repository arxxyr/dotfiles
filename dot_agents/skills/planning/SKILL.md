# 需求与实施规划

从现有上下文生成足以支持下一步工作的文档或工单，保持用户目标、范围和既有决策。
规划本身不表示获准实现代码、发布工单或启动自动执行。

## 选择模式

- 要求整理需求、形成 PRD：读取 [PRD 模式](references/prd.md)。
- 要求把方案、PRD 或计划拆成任务／工单：读取 [拆工单模式](references/issues.md)。
- 同时要求两者：先形成 PRD，再按其验收目标拆分工单，依次读取相应参考。
- 用户已给完整 PRD 时直接拆分；只要求 PRD 时不额外生成工单。

按实际交付物选模式，不要求用户先知道技能名称或专用命令。
如果“做个规划”的含义可由上下文推断，按最小完整交付推进并说明采用的形式。

## 收集必要依据

1. 读取已有对话、用户给出的方案、文档或工单；引用现有工单时核对正文与影响范围的讨论。
2. 有仓库时检查相关实现与测试，识别现状、可复用能力和会影响范围的集成边界。
3. 存在领域词汇表、上下文映射或 ADR 时，只读取当前功能涉及的部分并沿用其概念。
4. 将确定事实、已确认决策、建议和待定事项分开，不能把推断写成用户要求。

从已有材料综合，不重新访谈已经确定的需求。
仅在缺失信息会实质改变范围、契约或验收时提出聚焦问题；其他部分继续形成可评审草稿。
遇到未解决的关键设计取舍，先明确缺口；需要互动压力测试时使用可用的 `design-review`。

## 交付与工单集成

默认在对话中给出 Markdown 草稿；用户要求落盘时使用其路径或项目现有文档位置。
“写 PRD”“拆工单”本身不自动发布到远程系统；“在该项目创建工单”等明确请求即包含发布授权。
发布请求已有目标、内容范围和必要权限时直接执行，不增加固定的第二次审批。
只有需要实际工单集成时才读取项目的 tracker 配置与标签约定。
配置缺失且现有上下文不能补足时，才使用可用的 `setup-matt-pocock-skills`；普通本地规划不调用它。
初始化技能不可用时从项目配置或已连接工具获取必要信息，只询问仍缺失的具体目标。
缺少发布授权或目标时先完成可审阅草稿；授权与目标均明确后再执行依赖它的外部操作。

标签遵循用户要求与项目明确约定；不默认添加 `ready-for-agent`、指派人员或触发执行。
发布子工单不自动关闭、改写父工单或修改其状态；这些操作需要任务范围覆盖。
遇到发布结果不确定时先查询核实，避免重试生成重复工单。

## 完成检查

- 文档范围、建议和验收方式相互一致；未定事项明确可见。
- 工单各自有可观察的结果，依赖无环，合起来覆盖已承诺范围。
- 本地交付报告实际文件路径；远程交付报告已创建链接及未完成项。
- 不把“计划可供实施”表述为“已经实施”，不把草稿表述为“已经发布”。
