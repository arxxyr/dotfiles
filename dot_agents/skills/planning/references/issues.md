# 拆工单模式

围绕独立可验证的行为拆分实施工作，使每张工单的执行者在前置依赖满足后可以完成一段明确结果。

## 切分原则

- 优先从最小可用端到端路径开始，再增加业务变体、异常处理与兼容能力。
- 每片贯通实现该行为实际需要的层；纯 CLI、库或后台任务不为了模板虚构 UI、API 或数据库。
- 避免只按“数据库／后端／前端”形成互相等待且无法验收的水平任务。
- 确实需要共享基础设施或迁移前置项时允许单独拆出，但必须有独立可验证产物及明确消费方。
- 大小以验收边界与独立完成程度判断，不追求固定工单数，也不为每个文件创建一张工单。
- 从源需求追踪覆盖关系，遗漏的承诺补齐，重复切片合并或明确边界。

## 每张工单写什么

沿用项目已有模板；没有模板时写清下列内容：

1. 简短标题与要交付的行为，必要时用一个输入到结果的例子。
2. 范围和必要契约，包括会影响实现的状态、兼容或失败处理要求。
3. 可观察的验收条件及适当验证方式；前置工单完成后可独立判定通过。
4. 阻塞依赖和原因，没有依赖就写可立即开始；有父 PRD／工单时附引用。
5. 未决选择、外部条件或人工配合，仅在确实存在时列出。

“可自动实施”只表示执行时不依赖新的产品决策，不表示已经授权发布、部署或合并代码。
如果确实有架构取舍、人工验收或外部协调，把具体待办和解除阻塞条件写清；不要仅贴一个含糊的人工标签。
不强制使用 `HITL`／`AFK` 分类；项目已有约定或用户需要时再使用。

## 组织依赖

先用稳定的本地编号表示工单及依赖，检查无环和冗余依赖，并指出可以并行的部分。
依赖应指向需要的能力、数据或接口，不因表格中的先后顺序就添加阻塞边。
每个切片在依赖满足后应可单独演示或验证；若仍必须与另一工单同时交付，检查是否切错边界。
用简短列表或依赖表展示整体拆分，只有图能明显帮助理解时再画图。

## 已授权的发布

先确保每张草稿的标题、验收和依赖可审阅；是否需要再次确认由任务中尚缺的决策决定，不设固定审批轮次。
核对仓库／项目和同范围已有工单，按依赖顺序发布，使用实际返回的编号替换本地依赖引用。
优先使用 tracker 支持的依赖功能；不可用时在正文明确引用，不虚构已建立机器可识别的阻塞关系。
使用原有工单时不要仅为套用新模板而覆盖其讨论或已有内容。
发布中断时保留本地编号到远端链接的对应关系，报告成功与失败项；恢复前先核实已创建结果以免重复。
只有任务明确覆盖父工单更新、标签、指派或状态变化时才执行相应操作。
