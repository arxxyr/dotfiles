# PRD 模式

将已有需求综合成实现者可以据此理解目标、界定范围并验证结果的文档。规模跟随实际需求，不为完整模板虚构故事或指标。

## 建议内容

按项目已有模板组织；没有模板时可用以下内容，相关信息很少的部分可合并：

- 问题与目标：谁遇到什么问题，当前行为是什么，完成后将有什么可观察的变化。
- 范围与非目标：本次承诺的用户能力、主要边界和明确排除的工作。
- 用户场景与验收：正常路径、实质影响正确性的边界或失败场景，以及各自可判定的结果。
- 已确定的设计：模块职责、接口与数据契约、状态规则、兼容或迁移要求；不要将自己的建议标成已确认。
- 验证安排：按风险说明如何验证外部行为、集成契约与迁移结果，复用项目已有验证方式。
- 未决事项与依赖：仍需确认的产品选择、外部条件及其对实施范围的影响。

需要后续拆工单时可给场景或验收项分配稳定编号，便于追踪覆盖关系。
只写实际需要的用户场景，不要求固定句式或冗长清单。
性能、容量、安全等要求必须有业务或环境依据；未知目标标为待定，不编造数字。

## 实施信息的粒度

记录影响实现结果的约束与决定，不预先锁死尚无依据的文件布局或技术选型。
源码位置可作为现状证据，并注明其用途；避免把易变路径当作长期接口契约。
原型中表达状态机、数据形状或协议的短片段能减少歧义时可以保留，注明来源与适用边界。
复用现有模块时说明职责为何适合，不为了形式完整强行拆出新模块。
验证方案优先覆盖可观察行为，不机械要求每个模块各写一套测试或重述通用测试原则。

## 交付前核对

每项承诺都有验收依据；范围与非目标无冲突；待定决策没有伪装成事实。
若关键问题尚未解决，交付可用草稿并指出哪些部分会随答案变化。
生成 PRD 后按入口规定交付，不能仅因为文档已写完就发布到 tracker 或进入实施。
