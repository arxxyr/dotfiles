# 实施简报

简报把已有工单整理为执行者能理解、实施和验收的约定。它可以是对话草稿、项目文件或工单评论，交付位置由当前请求决定；转为 `ready-for-agent` 不自动生成或发布简报。

## 写作依据

- 先读原工单与相关讨论，保留已经确认的范围、需求和验收条件。
- 有冲突或缺口时明确列出，不能仅因新简报更整齐就用它覆盖原有决定。
- 描述当前行为、目标行为、关键接口与兼容边界，说明执行者需要达成什么结果。
- 优先使用稳定的类型、接口和业务契约；文件路径、行号可作为当前证据，但不能取代行为描述。
- 不预先锁死无依据的代码布局或实现步骤；确有必要的技术约束应解释原因。
- 验收条件必须具体、可观察，覆盖本次承诺和重要失败路径；写清非目标与依赖。
- 人工实施简报使用相同结构，并说明实际需要的判断、访问权限或人工验证。

## 建议结构

遵循项目已有模板；没有模板时可使用以下结构，不为填满章节虚构内容：

```markdown
## 实施简报

类别与目标：要修复的问题或交付的能力。
当前行为：已验证事实及相关证据；尚未复现的部分明确标注。
期望行为：可观察结果、重要边界及兼容要求。
关键契约：相关类型、接口、数据形状与需要保持的不变量。
验收条件：独立可判定的结果及适当验证方式。
范围与依赖：不做什么、依赖哪项能力、还有哪些未决问题。
依据：原工单、已确认讨论、设计记录及当前实现位置。
```

例如缓存失效问题，验收可写成“条目过期后首次读取返回新值；并发读取只触发一次刷新；刷新失败时保留已约定的错误语义”，但仅在这些确为当前任务要求时使用。
不要以“修好缓存”代替验收，也不要从示例推导新的产品要求。

## 交付边界

- “写一份简报”默认交付对话草稿；要求保存文件时才写入指定或项目惯用位置。
- 明确要求将简报发布到目标工单时直接发布，不另加固定审批；发布前核对目标和已有内容。
- 发布评论不自动改标签、指派人员、触发执行、关闭工单或修改原正文。
- 简报准备好不表示已实现、已验收或已授权自动运行 agent。
- 外部发布结果不确定时先查询核实，避免重复评论。
