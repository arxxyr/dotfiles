# 工单分诊

根据已有工单及项目证据判断下一步，区分评估建议与用户授权的实际操作。
新建需求或拆分实施任务使用 `planning`；普通诊断、测试不进入本流程。

## 请求范围与授权

- 查看、评估、审查、分诊建议：只读并在对话中给出结论，不评论、不改标签、不关闭工单、不写本地文件。
- 明确要求调整标签、发表评论、关闭工单或记录决定时，直接完成已授权操作，不增加固定确认轮次。
- 只要求改状态不自动补发实施简报；标记 `wontfix` 不自动关闭；关闭不自动写 `.out-of-scope/`。
- 没有指定目标或关键决定尚不清楚时，先形成可审阅建议，只询问影响操作的缺口。
- 参考资料只复用内容结构与记录方式；其示例中的评论、文件修改和关闭步骤不扩展本次授权。

## 获取项目依据

读取工单正文、相关讨论、标签与时间信息，识别已回答的问题和已有分诊结论。
结合相关代码、测试、领域词汇表和 ADR 核对事实，避免把报告者推测直接当成根因。
存在 `.out-of-scope/` 时只检查与当前概念相关的记录，历史拒绝不能自动决定新工单的结果。
需要工单集成时先使用现有项目配置与已连接工具；标签含义能从上下文确定就直接复用。
只有实际集成缺少必要配置且无法从现有资料得到时，才使用可用的 `setup-matt-pocock-skills`。
缺少初始化技能不阻止本地评估；明确指出无法核实的映射或目标即可。

## 分类与状态

优先遵循项目现有类别、标签与流程；以下是常见语义，不强制创建同名标签：

| 角色 | 含义 |
|---|---|
| `bug` / `enhancement` | 缺陷／能力改进 |
| `needs-triage` | 尚需评估 |
| `needs-info` | 缺少足以判断或复现的信息 |
| `ready-for-agent` | 行为、边界和验收已明确，可自主实施 |
| `ready-for-human` | 仍依赖人工判断、访问条件或实际操作 |
| `wontfix` | 已决定不处理 |

发现冲突标签时说明冲突；用户已明确要求目标状态时按项目约定直接修正相关标签。
不强制每张工单先经过 `needs-triage`，也不因为转移路径少见就重复请求已给授权。
实施就绪状态不代表已授权自动实现、部署或合并。

## 执行评估

1. 查看待办时，列出未分类、等待评估、补充信息后待复评的工单，给出数量和简短原因。
2. 对具体工单提出类别、状态与处理建议，附相关证据和缺口；紧急程度按实际影响判断。
3. 缺陷需要核实且环境允许时，做适当的只读诊断或本地复现，报告成功、失败或无法复现的具体原因。
4. 需要澄清关键设计取舍时使用可用的 `design-review`；已明确的状态操作直接执行，不强制访谈。
5. 需要撰写实施简报时读取 [实施简报参考](AGENT-BRIEF.md)，说明现状、目标、契约、验收及范围。
6. 用户要求持久化拒绝理由时读取 [范围记录参考](OUT-OF-SCOPE.md)，复用对应概念记录并保留决策依据。

`needs-info` 建议写清“已确认事实”和“还需要什么”，问题应可回答，不重复追问已有答案。
人工实施建议说明具体阻塞条件，不能只贴人工标签。
获准写出的内容遵循项目已有格式，不强制添加统一免责声明或额外仪式。

## 交付与恢复

评估任务交付建议及依据；执行任务核实实际结果并给出受影响工单链接。
外部操作结果不确定时先查询核实，再决定是否重试，避免重复评论或反复改状态。
续接分诊时优先核对新回复与旧缺口，只处理仍未解决的问题。
