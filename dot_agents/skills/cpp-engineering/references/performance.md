# C++ 性能与类型边界

## 先测量

- 使用 Release、代表性输入和稳定基准，记录吞吐、分配或 p99 等与目标相关的指标。
- Linux 可用 `perf` 与火焰图定位热点；不要只凭源码复杂度猜测瓶颈。
- 先消除多余分配、重复工作和不必要的所有权，再评估并行化。
- 优化必须保持行为、对象生命周期、线程安全与序列化协议；基准倍数不能跨环境外推。

## 布局与所有权

- 按大小/对齐需求排列字段可减少填充，但要在目标 ABI 上用 `sizeof`、`alignof` 验证。
- `u64 → u32 → u16 → u8` 只是候选顺序；不同目标 ABI、伪共享和访问模式可能改变选择。
- 不能重排外部 ABI、FFI、磁盘或网络布局中的字段；先查接口与格式契约。
- 连续结构体布局优化与缓存行隔离是不同问题，不能只追求最小体积。
- 用 `const Request&` 表达只读借用，用 `unique_ptr<Request>` 参数表达所有权转移。
- `string_view`、`span` 和引用不得超过底层数据生命周期，也不能跨可使其失效的修改。
- 用 `UserId`、`Email` 等不同类型避免相同底层表示造成的参数混淆。

## 并发与错误

- `jthread` 析构会等待线程结束；退出路径必须响应停止并能唤醒阻塞等待。
- `stop_token` 只表达协作取消，不会中断所有系统调用；检查等待原语和对象析构顺序。
- 任务图用 Taskflow 时明确输入、输出和共享状态依赖，避免遗漏边导致竞争。
- 错误路径保留足够诊断信息；不要用空 `optional` 混淆“没有数据”和不同失败原因。
- C++20 以现有结果类型或 `variant<Data, LoadError>` 表达错误，C++23 才考虑 `std::expected`。
- 在测量支持的情况下调整布局、分配器或线程策略，并用相关 Sanitizer 检查正确性。
